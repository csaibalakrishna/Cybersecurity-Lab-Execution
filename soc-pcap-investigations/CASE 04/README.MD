# Day 4 — ARP Spoofing Investigation

## Objective

Investigate a packet capture for signs of ARP spoofing by analyzing ARP requests and replies, identifying conflicting IP-to-MAC address mappings, and determining whether the observed traffic is consistent with ARP poisoning.

## 2. Methodology

The investigation focused on:

## 6. Suspicious Packet Analysis

### Packet 2282

**Ethernet II**

| Field | Value |
|---|---|
| Source MAC | `50:00:33:33:33:33` |
| Destination MAC | `50:00:22:22:22:22` |

**ARP Reply**

| Field | Value |
|---|---|
| Sender MAC | `50:00:11:11:11:11` |
| Sender IP | `192.168.1.1` |
| Target MAC | `50:00:22:22:22:22` |
| Target IP | `192.168.1.2` |

The ARP payload advertised:

```
192.168.1.1 is at 50:00:11:11:11:11
```

Wireshark generated the warning:

```
Duplicate IP address detected for 192.168.1.1
```

**Frame-level inconsistency:** The Ethernet source MAC (`50:00:33:33:33:33`) does **not** match the ARP sender MAC in the payload (`50:00:11:11:11:11`). In legitimate ARP traffic, the device sending the frame is the same device whose MAC is being advertised in the ARP payload. Here they diverge — the frame was transmitted by one MAC while claiming ownership of `192.168.1.1` under a different MAC. This mismatch is a stronger indicator of a crafted/spoofed reply than the duplicate-IP warning alone, since it shows the packet was not generated by the device that legitimately owns that address.

### Packet 2294

Repeated the same suspicious ARP mapping:

```
192.168.1.1 → 50:00:11:11:11:11
```

Wireshark again flagged the packet with a duplicate IP address warning. The repeated advertisement matters because the conflicting mapping was not limited to a single isolated packet.

---

## 8. What the PCAP Proves

- `192.168.1.1` was advertised with two different MAC addresses during the capture.
- Packets 2282 and 2294 repeated the conflicting mapping — not a one-off anomaly.
- The Ethernet frame source MAC and the ARP payload sender MAC disagree in packet 2282, consistent with a crafted reply.
- Wireshark's built-in duplicate-IP detection independently flagged the same conflict.

## 9. What the PCAP Does NOT Prove

- The real-world identity of the system generating the spoofed replies.
- Whether the activity was malicious or an authorized security test (e.g., an ARP-spoofing tool used in an approved assessment).
- Downstream impact — whether traffic was actually intercepted, modified, or relayed (a full MITM) as a result of the poisoned cache.
- Which host initiated the spoofing versus which host(s) were affected/poisoned by it.

Attribution requires additional evidence: endpoint telemetry, network inventory, or authorized network-scanning/pentest records.

---

## 10. Conclusion

The packet capture contains conflicting ARP mappings for `192.168.1.1`, where the same IP address is associated with multiple MAC addresses during the observed traffic.

The repeated conflicting ARP advertisements in packets 2282 and 2294, the Ethernet/ARP-payload MAC mismatch, and Wireshark's duplicate IP address detection are collectively consistent with **ARP spoofing / ARP poisoning** behavior.

The packet capture alone does not prove the real-world identity or intent of the system generating the traffic.

## 11. MITRE ATT&CK Mapping

| Tactic | Technique | ID |
|---|---|---|
| Credential Access / Collection | Adversary-in-the-Middle | [T1557](https://attack.mitre.org/techniques/T1557/) |
| Credential Access / Collection | Adversary-in-the-Middle: ARP Cache Poisoning | [T1557.002](https://attack.mitre.org/techniques/T1557/002/) |

ARP spoofing is used to redirect traffic intended for a legitimate host (here, `192.168.1.1`) to an attacker-controlled MAC address, enabling interception or manipulation of subsequent traffic. T1557.002 is the specific sub-technique for ARP-based cache poisoning, distinct from DNS spoofing or other AiTM methods under the parent technique.

---

## 12. Defensive Recommendations

1. Enable **Dynamic ARP Inspection (DAI)** where supported.
2. Use static ARP entries for critical systems where appropriate.
3. Monitor for unexpected changes in IP-to-MAC mappings.
4. Alert on repeated unsolicited ARP replies.
5. Investigate duplicate IP or conflicting MAC address warnings.
6. Maintain an accurate asset inventory to validate legitimate network devices.

---

## 13. Key Takeaway

ARP analysis should focus on consistency. A single IP address suddenly being associated with multiple MAC addresses is an important anomaly and can indicate ARP spoofing or poisoning.

The most important lesson from this investigation was distinguishing between what the packets prove and what is inferred: the PCAP proves conflicting ARP mappings; the repeated behavior is consistent with ARP spoofing, but the PCAP alone does not prove the identity or intent of the source.
